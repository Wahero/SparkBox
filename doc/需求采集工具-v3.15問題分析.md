# 需求采集工具 v3.15 問題分析

> 分析對象：`需求采集-通用版v3.15-261008.html`（資料庫 web 節點 `QupFJMgQi58sPPTOdNx2ux`）
> 對照：v3.1 設計文檔（`nA9uZFyJ2C6d59dijegJev`，狀態：v3.1 改造「尚未實現」，但實際 HTML 已迭代到 v3.15）
> 目的：這份工具是要**發給終端用戶填寫需求、存下內容、再發回收集方**的，所以「填寫者看得見的預覽」與「發出去的數據」都要可靠。

## 結論先行

1. **導出數據（文字 / JSON）本身是對的**——收集方收到的內容無誤。
2. **但手機上的「預覽」頁有 5 個欄位顯示錯誤**，且全是核心欄位。這會直接打擊填寫者信任、降低「發回」轉化率（這工具的核心價值就是打通最後一公里）。
3. 另有 **1 個跨項目草稿串檔隱患**，在多客戶場景下可能發錯資料。
4. 工程底子很好（polyfill、no-JS 自證、打印走隱藏 iframe、Web Share 優先＋降級面板、零網路請求合規），這些要保留。

## 一、已確認的 Bug

### 🔴 P0｜預覽頁 5 個欄位永遠顯示「未填 / 未選」（最高優先）

| 欄位 | 預覽現象 | 真正原因 | 出問題位置 |
|---|---|---|---|
| 最想解決的問題（f_pain） | 永遠「未填」 | CARDS 裡被誤標 `'multi'`，但它是 textarea，沒有 `data-multi`，`MULTI.f_pain` 不存在 → 取到空 | `CARDS` 陣列（約 line 610） |
| 希望有哪些功能（f_want） | 永遠「未填」 | 同上，誤標 `'multi'` | `CARDS`（約 line 611） |
| 明確不要做的（f_nowant） | 永遠「未填」 | 同上，誤標 `'multi'` | `CARDS`（約 line 611） |
| 系統會收集個人信息嗎（f_pi） | 永遠「未選」 | `render()` 對 risk 模式讀 `g(id)`（= 輸入框值），但這題是單選，值存在 `SINGLE[id]`，沒有對應 input → 永遠空 | `render()` 取值（約 line 642） |
| 要不要 AI 參與判斷（f_ai） | 永遠「未選」 | 同上 | 同上 |

**為什麼嚴重**：第 1–3 題是整份需求最有價值的「痛點 / 期望」內容；第 4–5 題是設計文檔明寫「影響合規要求和項目周期」的確認題。它們在**填寫者按「查看預覽」核對時全部看不到**，用戶極可能以為工具壞了而放棄發回。

**修法（極小改動）**：
- `CARDS` 中把 `f_pain / f_want / f_nowant` 的第三個元素 `'multi'` 拿掉（它們本就是普通文字框）。
- `render()` 取值改為：`mode === 'multi' ? L(MULTI[id]) : (mode === 'risk' || mode === 'single' ? (SINGLE[id] || '') : g(id))`。

> 驗證點：`build()`（文字導出）、`snapshot()`（JSON）、`buildHtml()`（HTML 報告）這三處**都是正確的**，所以收集方拿到的數據沒錯，只有「填寫者預覽」這一處錯。

### 🟠 P1｜跨項目 / 跨客戶草稿串檔

- 全站只有一個 localStorage key `req_draft_v3`，**base 表單草稿不區分項目或客戶**。
- v3.15 只給「改寫版（manual）」做了身份綁定（`manualSig`），但**整份 base 草稿仍是全站共用**。
- 場景：同一台手機 / 同一瀏覽器幫 A 客戶填完，隔天幫 B 客戶打開工具，`load()` 會直接載入 A 的資料；若沒先點「清空」，預覽與發回都延續 A 的內容。
- 風險：誤把 A 客戶資料發給 B；或用戶以為是空白表其實已有舊資料。
- 修法（擇一）：
  1. 草稿 key 按「行業 + 項目名 + 聯絡方式」或一組隨機 `sessionId` 區分；
  2. 或更簡單：「儲存」成功後自動 `doReset()` 清掉 base 草稿（改寫版已進 JSON，不會丟）。

### 🟡 P2｜預覽與「發送內容」不一致（手寫改寫場景）

- 當存在「我的文字版」（manual 改寫）時，預覽**同時**顯示「改寫版卡片 + 結構化卡片」，但 `effectiveText()`（複製 / 發送）只取改寫版自由文本。
- 用戶以為發出去的包含結構化欄位，實際只有自由文本 → 預期落差。
- 修法：改寫版模式下預覽**只顯示改寫版**（與發送一致），或加一行明確提示「已用手寫版替代自動生成內容」。

### 🟡 P2｜iOS `file://` 下「複製」可能靜默失敗

- `copyText()` 先走 `execCommand('copy')`（已廢棄，iOS Safari 常攔截），回退 `navigator.clipboard.writeText`（需安全上下文，`file://` 不一定可用）。
- 失敗時只提示「請長按文字手動複製」，並未真正複製。可接受，但建議把「發給對方」面板裡的全文預覽框做得更易長按。

### 🟢 P3｜啟動即 `confirm` 詢問續填

- `askResume()` 在 `boot()` 彈 `confirm`，對「忙碌 / 沒耐心」的目標用戶略突兀；`file://` 下少數 WebView 的 `confirm` 行為不穩。
- 修法：改成非阻塞的頂部輕提示 ＋「清空重填」按鈕。

- 頂部版本欄 ＋ 環境 / 按鈕綁定自檢

## 六、✅ P1 修復狀態（2026-10-10 已完成，含一輪 regression 修正）

**根因**：`var LS = 'req_draft_v3'`（第 440 行）全站唯一 key，`save()/load()/doReset()` 都用佢，base 草稿跨客戶串檔。

**改法（方案 A 精準版）**：導出／分享「成功」後才清 localStorage 草稿，只 `removeItem(LS)`、唔動內存、唔跳頁。新增 `clearDraft()`，在「真正導出成功」的出口呼叫：

| # | 位置 | 出口 |
|---|------|------|
| 1 | `copyText()` 第 1103 行 | 複製成功（execCommand）→ `clearDraft()` |
| 2 | `copyText()` 第 1106 行 | 複製成功（clipboard）→ `clearDraft()` |
| 3 | `dl()` Web Share `.then` 第 1019 行 | 分享成功 → `clearDraft()` |
| 4 | `dl()` 桌面分支 | 桌面原生下載成功 → `clearDraft()`（取代原先 `actSave` 的清除點）|
| 5 | `fallbackSave()` 第 1058 行 | 降級面板「下載」成功 → `clearDraft()` |

**regression 修正（同輪）**：初版把 `clearDraft()` 加在 `actSave()` 第 1182 行 `dl()` 之後，導致手機端走 `fallbackSave` 面板時，`actSave` 仍會在面板彈出後立刻 `tip('已储存')` 並清 LS —— 既出現「已儲存」誤導提示，又造成「草稿清了但用戶還沒拿到檔」的雙失風險。已將 `actSave` 的 `tip + clearDraft` 移除，改由桌面分支（真正下載成功）及面板「下載／複製」按鈕（用戶主動拿到數據）負責清除；「已儲存」提示改為僅桌面下載成功才出現。

**驗證**：`vm` + DOM stub 實跑，三種環境確認：
- 桌面 `actSave()` 後 LS 已清（✓ 下載成功才清）
- 手機 `actSave()`（fallback 面板）後 LS **仍在**（✓ 不再過早清，雙失風險消除）
- 手機面板撳「下載」後 LS 已清（✓ 用戶主動導出才清）

**效果**：填完 → 導出／分享成功 → 草稿清走 → 下次打開係空白新表，唔會載到上一位客戶。中途改嘢仍會 `save()` 寫回 LS（保留續填），只有「成功導出」才清。

### 6.1 追加修正（2026-10-10 晚）：降級面板「點擊即關閉」

**問題**：手機 fallback 面板（`#ovSave`）撳完「下載 / 存儲到文件」或「複製內容」後，面板唔會自動收起，用戶要再撳「關閉」先退出，體驗多餘。

**改法**：喺 `fallbackSave()` 內 `ovSaveDl` / `ovSaveCopy` 兩個 `onclick` 末尾加 `closeSave()`，撳完即自動關閉面板（「關閉」按鈕照常保留作備用）。`clearDraft()` 仍喺「下載」出口觸發，草稿照常清。

**驗證**：`node --check` 語法 OK；`vm` 實跑確認面板彈出 `overlay on` → 撳「下載」後變 `overlay`（已關閉）且 LS 已清 → 重新彈出再撳「複製內容」後同樣變 `overlay`（已關閉）。三者 PASS。

### 6.2 追加修正（2026-10-10 晚）：手機「下載」攞唔到檔 / JSON 複製到空內容

**用戶回報**：手機撳「存儲」→「下載」後，本地搵唔到檔。

**根因（兩層）**：
1. `fallbackSave()` 用 `/^text\//` 判斷文字型 blob，`application/json` 唔中 → `ov.__text=''`、文字框隱藏。結果微信環境下撳「複製內容」會複製到**空字串**——微信用戶唯一可靠出路被廢。
2. 降級面板「下載」只靠 `anchorSave()`（`<a>.click()`），喺**微信內置瀏覽器 / 部分 WebView 會被靜默攔截** → 冇檔、冇提示。

**改法**：
- `fallbackSave()` 嘅 `isText` 判斷加 `/json/i`，JSON 當文字處理（可預覽＋可複製）。
- 「下載」按鈕改環境感知：偵測到 `MicroMessenger` UA → 直接 `copyText()` 內容（最穩，可貼去微信聊天傳回收集方）；其餘環境先試 `navigator.share({files})`「存到文件」、失敗再降級 `anchorSave()`、再唔行就複製兜底。

**驗證**：`node --check` OK；`vm` 實跑兩環境：
- `[微信MicroMessenger]`：面板彈出 → JSON 轉為可複製文本（596 字符）→ 撳「下載」後面板關閉 + LS 已清 + **複製到非空 JSON（596 字符）** ✓
- `[一般手机-无WebShare]`：同樣面板關閉 + LS 已清 + 複製到非空 JSON ✓
（真·iOS Safari / 安卓 Chrome 走 Web Share「存到文件」，係獨立於面板嘅 `dl()` 路徑，未受影響。）

> 註：手機環境若唔支援 Web Share，`dl()` 會彈 `fallbackSave` 面板（「下載／存儲到文件」＋「複製內容」），呢個係**預期降級**而非崩潰——用戶要在面板度撳「下載」或「複製」才真正拿到數據，再按「關閉」離開。若想「撳完即自動關閉面板」可再加（見 P2/P3 之外的小優化）。
